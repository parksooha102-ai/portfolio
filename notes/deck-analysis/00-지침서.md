# 기술문서 → PPT 분석 지침서

Nov 27, 2026 · @박수하

## 목적과 쓰는 법

이 지침서는 기술문서로 슬라이드를 만들기 전에 무엇을 말하고 무엇을 보여줄지 먼저 정하는 기준입니다. 분석이 끝나면 **슬라이드 설계표** 하나가 나오고, 제작은 그 표를 따라 합니다.

- **입력**: 기술문서 (설계서, API 문서, 논문, 운영 매뉴얼, 장애 보고서 등)
- **출력**: 슬라이드 설계표. 한 행이 한 장이고, 장마다 메시지·시각 자료·배치·글을 적습니다 (산출물 절 참고).
- **순서**: 원칙 확인 → 분석 절차대로 진행 → 시각 자료·배치·코드 절을 보며 장마다 결정 → 점검표로 확인
- **범위**: 분석 단계에서는 색, 글꼴, 템플릿 같은 디자인은 정하지 않습니다. 무엇을 어떤 모양으로 보여줄지까지만 정합니다.

## PPT 원칙

모든 판단은 아래 여섯 원칙을 따릅니다. 오른쪽 칸은 분석할 때 그 원칙을 어떻게 적용하는지입니다.

| 원칙 | 분석할 때의 판단 기준 |
| --- | --- |
| 1. 사람이 이해하기 위한 것입니다. 기술문서를 베끼어 옮기지 않습니다. | 문서의 목차와 문장을 옮기지 않고, 청중이 궁금해할 순서로 다시 짭니다. 문서 문장이 화면에 그대로 남아 있으면 다시 씁니다. |
| 2. 핵심만 집습니다. 한 장에는 말하려는 것 하나만 담고, 문장 대신 짧은 구절로 씁니다. | 장 제목을 주장 한 구절로 쓸 수 있어야 합니다. 글은 서술어와 접속사를 빼고 명사·숫자 중심 구절로 씁니다. |
| 3. 시각 자료가 중심입니다. 그림, GIF, 다이어그램, 비교 표가 화면의 주인공이고, 글은 그 옆의 설명입니다. | 장마다 "무엇을 보여줄까"를 글보다 먼저 정합니다. 글에는 자료가 보여주지 못하는 것(이유, 숫자의 의미, 주의점)만 남깁니다. |
| 4. 빈 곳 없이 채웁니다. 자료 크기에 맞춰 배치를 고르고, 정해진 틀에 억지로 끼워 넣지 않습니다. | 자료의 가로세로 비율과 개수를 먼저 보고 배치를 고릅니다. 남는 공간은 자료를 키우거나 확대 상세로 채웁니다. |
| 5. 글 위주 화면은 지양이지 금기가 아닙니다. 꼭 필요하면 글이 중심인 장도 둡니다. 그런 장을 피하려고 내용을 억지로 빼거나 합치지는 않습니다. | 그림으로 바꿀 수 없는 내용(정의, 원칙, 제약 조건 목록 등)은 글 중심 장으로 둡니다. 설계표에 "글 중심"이라고 밝혀 둡니다. |
| 6. 코드를 설명하는 장에서는 코드 스니펫이 그림을 대신합니다. 그 장에는 따로 그림을 찾지 않고, 스니펫을 시각 자료로 삼아 배치합니다. | 코드 장은 스니펫이 시각 자료 칸을 차지합니다. 스니펫을 고르고 강조하는 법은 코드 설명 장 절을 따릅니다. |

## 분석 절차

분석은 일곱 단계로 진행합니다. 뒷 단계에서 문제가 보이면 앞 단계로 돌아갑니다. 특히 흐름 점검(7)에서 끊기는 곳이 보이면 장 나누기(3)로 돌아갑니다.

1. **청중과 목적 정하기**
   - 누가 보는가: 개발자, 기획·운영, 경영진, 처음 보는 사람. 사전 지식 수준을 한 줄로 적습니다.
   - 보고 나서 무엇을 할 수 있어야 하는가: "이해한다", "결정한다", "따라 할 수 있다" 중 하나로 적습니다.
   - 발표 시간은 적되, 장 수는 미리 정하지 않습니다. 장 수는 내용이 정합니다.
   - 문서 종류를 파악합니다. 종류마다 핵심이 놓인 곳이 다릅니다. 설계서는 구조와 결정 이유, API 문서는 호출 흐름과 예제, 논문은 문제·방법·결과 수치, 매뉴얼은 절차, 장애 보고서는 경과·원인·조치입니다.
2. **핵심 메시지 뽑기**
   - 문서 전체를 한 문장으로 요약합니다. 이 문장이 발표의 결론입니다.
   - 섹션마다 "그래서 무엇이 중요한가"를 한 구절로 적습니다. 배경, 용어 정의, 부록은 청중에게 필요한 만큼만 남깁니다.
   - 문서 순서가 아니라 청중의 질문 순서로 다시 놓습니다. 흔한 순서는 왜 필요한가 → 무엇인가 → 어떻게 동작하나 → 결과·효과 → 한계와 다음 단계입니다.
3. **장 나누기**
   - 메시지 하나가 한 장입니다. 장 제목은 주제어("캐시 구조")가 아니라 주장 구절("캐시 먼저, 없을 때만 DB")로 씁니다.
   - 제목에 "그리고", "및"이 들어가면 두 장으로 나눕니다.
   - 장 수를 줄이려고 내용을 빼거나 합치지 않습니다. 청중에게 필요한 메시지면 장을 둡니다.
4. **장마다 시각 자료 정하기**
   - 장 메시지를 가장 빨리 보여주는 자료를 시각 자료 절의 표에서 고릅니다.
   - 자료를 어디서 구할지 함께 적습니다: 문서 그림 재사용, 다시 그림, 화면 캐처, GIF 녹화, 코드 스니펫.
   - 문서 그림은 그대로 쓸지 따져 봅니다. 문서용 그림은 촘촘한 경우가 많아, 필요한 부분만 자르거나 단순하게 다시 그립니다.
   - 맞는 자료가 없으면 장식용 그림을 넣지 않고 글 중심 장으로 둡니다.
5. **글을 구절로 줄이기**
   - 자료가 이미 보여주는 것은 글로 되풀이하지 않습니다.
   - 한 구절은 한 줄 안에 끝냅니다. 서술어·조사·접속사를 빼고, 숫자와 고유명사는 살립니다.
6. **배치 고르기**
   - 자료의 비율, 개수, 글의 양을 보고 배치 절의 기준으로 고릅니다.
7. **흐름 점검**
   - 장 제목만 이어 읽어도 이야기가 되는지 확인합니다. 끊기는 곳은 2–3단계로 돌아가 고칩니다.
   - 마지막으로 점검표를 한 번 돌립니다.

### 문장을 구절로 바꾼 예

| 문서 문장 | 슬라이드 구절 |
| --- | --- |
| 본 시스템은 요청이 들어오면 먼저 캐시를 조회하고, 데이터가 없는 경우에만 데이터베이스에 접근하도록 설계되었다. | 캐시 먼저, 없을 때만 DB |
| 무중단 배포를 위해 블루-그린 방식을 채택하였으며, 전환은 로드밸런서 설정 변경으로 이루어진다. | 블루-그린 배포 · 로드밸런서로 전환 |
| 해당 설정값을 잘못 지정할 경우 서비스 전체가 재시작될 수 있으므로 주의가 필요하다. | 주의: 잘못 설정하면 전체 재시작 |

## 내용별 시각 자료 고르기

장 메시지가 어떤 모양인지 먼저 보고 자료를 고릅니다. 같은 내용이라도 무엇을 강조하느냐에 따라 자료가 달라집니다.

| 내용의 모양 | 쓸 자료 | 예 | 주의 |
| --- | --- | --- | --- |
| 구성 요소와 연결 관계 | 구성도(아키텍처 다이어그램) | 서비스 간 호출 관계 | 이 장에서 말할 부분만 강조하고 나머지는 흐리게 |
| 순서가 있는 절차 | 흐름도, 번호 단계 띠 | 배포 절차 | 분기·반복이 없으면 가로 단계 띠로 충분 |
| 주체끼리 주고받기 | 시퀀스 다이어그램 | 인증 요청과 응답 | 주체가 많으면 장을 나눔 |
| 상태가 바뀜 | 상태 다이어그램 | 주문 상태 전이 | 화살표에 전이 조건을 짧게 |
| 시간에 따라 움직이는 동작 | GIF, 단계별 스냅샷 | 드래그 동작, 로딩 과정 | GIF 하나에 동작 하나만, 짧게 반복 |
| 화면·UI | 스크린샷 + 강조 표시 | 설정 화면 | 볼 곳에 상자·번호 콜아웃 |
| 둘 이상 비교 | 비교 표, 전/후 나란히 | 기존 방식 vs 새 방식 | 같은 기준으로 행을 맞춤 |
| 수치·성능 | 차트(막대, 선) | 도입 전후 응답 시간 | 결론이 되는 숫자를 크게 |
| 시간 순서의 사건 | 타임라인 | 장애 경과 | 중요한 시점 하나를 강조 |
| 계층·분류 | 트리, 묶음 상자 | 모듈 구성 | 깊이가 길면 윗 단계만 |
| 데이터 구조 | 필드 표, 예시 JSON | API 응답 형식 | 설명할 필드만 남김 |
| 코드 동작 | 코드 스니펫 | 함수 구현 | 코드 설명 장 절을 따름 |
| 정의·원칙·제약 목록 | 글 중심 장(카드형 구절) | 용어 정의, 제한 사항 | 그림을 억지로 만들지 않음 |

설계표의 '준비' 칸에는 자료를 어디서 구할지 적습니다: 문서 그림 재사용, 다시 그림, 화면 캐처, GIF 녹화, 스니펫 중 하나입니다.

## 자료 모양에 맞춘 배치

배치는 자료의 가로세로 비율과 개수로 정합니다. 틀을 먼저 고르고 자료를 끼워 넣지 않습니다.

&#91;embedded content: 배치 유형 7가지 · 자료 모양별\]

색칠한 상자가 시각 자료, 회색 선이 글(구절)입니다. 자료 비율에 가장 가까운 유형에서 시작해, 실제 크기에 맞게 조정합니다.

### 빈 곳이 남을 때 (이 순서로)

1. 자료를 키웁니다.
2. 핵심 부분을 확대한 상세를 옆에 둡니다.
3. 번호·화살표 콜아웃으로 설명을 자료 위에 올립니다.
4. 그래도 남으면 배치를 바꿉니다 (예: 위아래 → 좌우).

빈 곳을 채우려고 글이나 장식 그림을 더하지 않습니다.

### 자료가 넘칠 때 (이 순서로)

1. 이 장 메시지에 필요한 부분만 잘라냅니다.
2. 글자가 읽히지 않을 만큼 작아지면 두 장 이상으로 나눕니다. 같은 그림을 두고 강조 위치만 옮기는 방식이 좋습니다.
3. 줄이려고 핵심 정보를 빼지는 않습니다.

## 코드 설명 장

코드를 설명하는 장에서는 스니펫이 시각 자료입니다. 그 장에는 그림을 따로 찾지 않고, 스니펫을 화면의 주인공으로 배치합니다.

- **코드 장으로 둘지 판단**: 청중이 그 코드를 직접 읽거나 고칠 사람이면 스니펫을 씁니다. 동작만 알면 되는 청중이면 흐름도나 시퀀스 다이어그램이 낫습니다.
- **고르기**: 파일 전체가 아니라 설명할 부분만 가져옵니다. 이 장 메시지와 관계없는 줄은 `…`로 줄여 생략한 것을 드러냅니다.
- **뜻을 바꾸지 않기**: 줄이더라도 원래 코드와 다르게 동작하는 것처럼 읽히면 안 됩니다.
- **강조**: 말하려는 줄을 하이라이트하거나 나머지를 흐리게 합니다. 설명 구절과 줄을 ①②③ 번호로 이어 붙입니다.
- **읽힘**: 발표 화면 뒤쪽에서도 읽히는 글자 크기를 지킵니다. 안 되면 줄을 더 줄이거나 장을 나눕니다.
- **긴 흐름**: 같은 스니펫을 여러 장에 두고 강조 줄만 옮겨 단계별로 설명합니다.
- **배치**: 스니펫은 대개 세로로 길어 왼쪽 스니펫 + 오른쪽 설명이 기본입니다. 짧고 넓으면 위 스니펫 + 아래 설명입니다.
- **실행 결과**: 출력이나 화면을 봐야 코드가 이해되면 결과를 스니펫 옆에 둡니다. 이것은 따로 찾은 그림이 아니라 코드 자료의 일부로 봅니다.
- **설계표 표기**: 시각 자료 칸에 "스니펫", 준비 칸에 파일명·줄 범위·강조할 줄을 적습니다.

## 산출물: 슬라이드 설계표

분석 결과는 표 하나로 정리합니다. 한 행이 한 장이고, 표 위에는 분석 절차 1–2단계의 결과(청중, 목적, 전체 요약 문장)를 적습니다.

### 칸 설명

| 칸 | 적는 것 |
| --- | --- |
| # | 장 번호 |
| 메시지 | 장 제목. 주장 한 구절 |
| 시각 자료 | 자료 종류와 무엇을 강조할지. 글 중심 장이면 "글 중심" |
| 준비 | 문서 그림 재사용 / 다시 그림 / 캐처 / GIF 녹화 / 스니펫(파일·줄 범위) |
| 배치 | 배치 절의 유형 중 하나 |
| 글 | 화면에 올릴 구절. 가운뎃점(·)으로 구분 |
| 원문 위치 | 근거가 된 문서 절 번호나 쪽 |

### 작성 예시

가상의 "주문 서비스 캐시 도입 설계서"를 개발팀에 설명하는 경우입니다.

| # | 메시지 | 시각 자료 | 준비 | 배치 | 글 | 원문 위치 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 주문 조회가 느린 이유: 매번 DB 직행 | 현재 구성도, DB 구간 강조 | 문서 그림 2를 단순하게 다시 그림 | 가운데 크게 + 콜아웃 | 요청마다 DB 조회 · 피크 때 대기 증가 | 1.2 배경 |
| 2 | 캐시 먼저, 없을 때만 DB | 시퀀스 다이어그램(적중·미적중 두 경로) | 다시 그림 | 위 전체 폭 + 아래 띠 | 적중 시 DB 생략 · 미적중 시 캐시 채움 | 3.1 |
| 3 | 캐시 조회 코드 | 스니펫, 조회·저장 줄 강조 | 스니펫: OrderService 조회 함수, 강조 줄 지정 | 왼쪽 스니펫 + 오른쪽 설명 | ① 캐시 조회 · ② 없으면 DB · ③ 캐시 저장 | 부록 A |
| 4 | 데이터가 바뀌면 캐시를 지움 | 흐름도(수정 → 캐시 삭제) | 다시 그림 | 위 전체 폭 + 아래 띠 | 수정 즉시 삭제 · 다음 조회 때 다시 채움 | 3.3 |
| 5 | 도입 전후 응답 시간 | 막대 차트(전/후) | 문서 표 4를 차트로 | 가운데 크게, 결론 숫자 강조 | 핵심 수치 하나만 크게 | 5.2 |
| 6 | 운영 시 지킬 제약 | 글 중심(카드 3개) | — | 3단 카드 | 만료 시간 기준 · 캐시 장애 시 DB 직행 · 키 이름 규칙 | 4.3 |

문서 순서대로라면 제약(4.3)이 결과(5.2)보다 앞서고 코드는 부록에 있습니다. 설계표에서는 코드를 그 동작을 설명한 장 바로 뒤로, 제약을 결과 뒤로 옮겼습니다. 6번은 그림으로 바꿀 수 없는 목록이라 글 중심 장으로 두었습니다.

## 점검표

설계표가 끝나면 아래를 확인합니다. 하나라도 걸리면 해당 단계로 돌아갑니다.

### 장마다

- [ ] 장 제목이 주제어가 아니라 주장 한 구절인가
- [ ] 메시지가 하나뿐인가
- [ ] 화면의 주인공이 시각 자료인가. 글 중심이라면 그림으로 바꿀 수 없는 내용인가
- [ ] 문서 문장을 그대로 옮긴 곳이 없는가
- [ ] 글이 자료가 보여주는 것을 되풀이하지 않는가
- [ ] 배치가 자료 비율에 맞고, 빈 곳이나 눌린 자료가 없는가
- [ ] 자료 속 글자가 발표 화면에서 읽히는가
- [ ] 코드 장에 따로 찾은 그림을 넣지 않았는가

### 전체

- [ ] 장 제목만 이어 읽어도 이야기가 되는가
- [ ] 문서 목차가 아니라 청중의 질문 순서를 따르는가
- [ ] 문서 전체 요약 문장이 결론 장에 드러나는가
- [ ] 장 수를 맞추려고 내용을 빼거나 합친 곳이 없는가

## 자주 하는 실수

| 실수 | 왜 문제인가 | 바로잡기 |
| --- | --- | --- |

| 다이어그램 안에 문장 | 그림이 다시 글 화면이 됨 | 상자에는 이름만, 설명은 옆 구절로 |
