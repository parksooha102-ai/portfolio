# /portfolio-build — 포트폴리오 데이터 생성

대상: `$ARGUMENTS` (비어 있으면 `src/`의 모든 프로젝트, 폴더 이름이면 그 프로젝트만 다시 만듦)

시작 전에 `CLAUDE.md`의 **반드시 지킬 원칙**을 다시 확인합니다. 핵심은 **지어내지 않기**와 **수강생 문서를 고쳐 쓰지 않기**입니다.

## 0. 준비 — 기준 읽기

1. [schema.md](schema.md) — 출력 형식 (반드시 이 형식대로)
2. `format/01-portfolio.md` — 포트폴리오 페이지·슬라이드·상세 문서에 무엇이 들어가는지, 체크리스트
3. `format/02-tech-document.md` — 5단 구조 판정 기준
4. `format/03-diagrams.md` — 다이어그램 점검 기준
6. `profile.md`

## 1. 프로젝트 찾기

- `src/*/`에서 `_`로 시작하지 않는 폴더 = 프로젝트. 폴더 이름이 곧 `id`.
- 프로젝트 문서 = 폴더 바로 아래의 `.md` 파일 (`프로젝트문서.md` 우선, 그다음 예전 이름 `기술문서.md`, 없으면 `README.md`, 그것도 없으면 유일한 `.md`).
  하위 폴더 `_intake/`(`/portfolio-intake`가 만든 재료집·촬영목록·발표자료와 `pptx/` 그림)는 **프로젝트 문서가 아니므로 읽지 않습니다**. 루트 `.md`가 없고 `_intake/`만 있으면 그 프로젝트는 건너뛰고 리포트에 "아직 재료집 단계입니다 — `_intake/`의 재료집·발표자료 질문에 답해 `프로젝트문서.md`를 직접 쓴 뒤 다시 실행하세요"라고 적습니다.
  `.md`가 없으면 그 프로젝트는 건너뛰고 리포트에 "프로젝트 문서 없음"으로 적습니다.
  (리포트의 자리: `## 프로젝트별 점검` 끝의 `### 건너뛴 폴더`, 등급 없이 한 줄씩 — 요약 표 개수에 넣지 않음. 폴더 하나만 다시 만들 때도 적음.)
  건너뛴 프로젝트마다 "무엇을 더 준비하면 되는지는 `/portfolio-check <폴더>`의 **재료 점검표**로 볼 수 있습니다"를 덧붙입니다
  (뼈대 칸마다 필요한 자료는 `format/07-materials.md`). 빌드가 재료 점검표를 직접 만들지는 않습니다.
- `images/`의 실제 파일 목록, `code/`의 `.cs` 목록(하위 폴더 포함 `code/**/*.cs`)을 Glob으로 확보해 둡니다.

## 2. 프로젝트별 추출

프로젝트마다 프로젝트 문서를 **끝까지** 읽고 [schema.md](schema.md)의 `data/projects/<id>.json`을 채웁니다
(`schemaVersion: 2`, 포트폴리오 페이지용 필드. **슬라이드 `deck`은 만들지 않습니다** — 아래 §2-2).
프로젝트가 3개 이상이면 **프로젝트마다 서브에이전트를 병렬로** 띄워도 됩니다
(각 에이전트에 `CLAUDE.md`·schema.md·format/01·02·03·04 경로와 이 단계·§4의 규칙을 넘김. profile.md는 필요 없음.
에이전트는 `data/projects/<id>.json`을 직접 쓰고 ① 문서 구성(뼈대 + 붙은 모듈, `format/02`) ② 점검 항목 ③ "확인해 주세요" 목록
④ 기술 스택 근거 후보(`기술 | 근거 문장 | 원문 섹션`) ⑤ 스크린샷·링크·code/ 통계를 돌려줌. portfolio.json·report.md는 부모가 씀).

### 2-1. 포트폴리오 페이지용 필드

- **원문에 있는 것만.** 문장은 압축해도 되지만 사실·수치·기술명을 더하지 않습니다.
- 무엇이 "그대로"이고 무엇이 "압축"인지는 [schema.md](schema.md)의 구분을 따릅니다. **압축한 필드**는 목록으로 기억해 두었다가 리포트 "확인해 주세요"에 넣습니다.
- `intent`(개발 의도): 개요에서 왜 만들었는지(무엇에 집중했는지)를 쓴 글에서 1~2문장. 원문 문장을 그대로 잘라 쓸 수 있으면 `verbatim: true`,
  줄이거나 합쳤으면 `verbatim: false`(→ "확인해 주세요"). 왜 만들었는지를 쓴 글이 없으면 `null`(그 자체는 format/02 기준으로 **필수** 항목이 됩니다).
- `highlights`: 문서의 **핵심 시스템/기능 섹션**에서 2~4개. `why`는 같은 기능의 "고민과 선택"에서 찾습니다.
  흩어져 있으면(기능 단위가 반복되는 문서) 해당 기능 근처의 선택 근거를 씁니다. 근거가 없으면 `""`.
  `image`: 그 기능의 `section` 절 안(표 밖)에 **실제로 있는** 이미지 하나(`src`·`w`·`h`·`caption`). 그 절에 이미지가 없으면 `null` — 다른 절의 그림을 가져오지 않습니다.
- `troubleshooting`: 문서의 문제 해결 사례(문제 → 원인 → 해결)에서 임팩트가 큰 순으로 최대 3개. 그 문제가 생긴 기능 장 안의 절이든 별도 장이든 같습니다.
- `retro`: 결론(회고) 장에서. 달성 = 목표한 경험이 어떻게 됐는지와 이룬 것, 아쉬운 점 → 계획 = 회고의 "겪은 일 → 다음에는"(schema.md).
- `screenshots`: `images/`에 **실제로 있는** 파일 중, 서로 다른 기능을 보여주는 최대 6장. 커버와 겹치지 않게.
- `retro.section`: 회고(결론) 장의 제목 글자 그대로(없으면 `""`).
- `section`: 원문 제목 텍스트를 **글자 그대로** 복사 (`### ` 같은 기호만 제외).
- `w`·`h`: 이미지 **파일 머리에서 읽은** 픽셀 크기만. 눈대중·문서에 적힌 숫자는 쓰지 않습니다. 한 줄 예(프로젝트 폴더의 `images/` 전체):
  - PowerShell: `Add-Type -AssemblyName System.Drawing; Get-ChildItem src\<id>\images\* | % { $i=[Drawing.Image]::FromFile($_.FullName); "$($_.Name) $($i.Width) $($i.Height)"; $i.Dispose() }`
  - 파이썬(Pillow가 있을 때): `python -c "import glob;from PIL import Image;[print(p,*Image.open(p).size) for p in glob.glob('src/<id>/images/*')]"`
  - 읽지 못한 파일(예: `.webp`)은 `w`·`h`를 **빼고** 둡니다(렌더러가 실행 중에 잼).
- 팀 프로젝트면 `team.role`을 반드시 찾습니다. 없으면 `""`로 두고 리포트 **필수** 항목.

### 2-2. 슬라이드 — 지금은 만들지 않음

예전 슬라이드 렌더러·디자인·장면 생성 규칙은 2026-11-27에 모두 지웠습니다(글이 너무 많고 빈 곳이 많은 슬라이드가 나와서). 새 방식을 정할 때까지:

- 프로젝트 JSON에 `deck`을 **쓰지 않습니다**. 예전 data에 `deck`이 있어도 이어 받지 않습니다.
- 슬라이드는 빌드가 아니라 `decks/<폴더>/deck.json`(설계표에서 옮김)이 정합니다. 빌드는 `decks/`를 건드리지 않습니다. 예전 장면 점검(`PFScene`)·`deck-edits.json`·`/portfolio-edit`는 없습니다.
- `schema.md`·`format/`·`docs/`에 슬라이드 이야기가 남아 있어도 따르지 않습니다.

## 3. 프로필·기술 스택

- `profile`·`settings`는 `profile.md`에서만. 자기소개는 줄바꿈까지 그대로.
- `profile.md` 값이 예시 그대로(홍길동, you@example.com, your-id)면 그대로 싣되 리포트 **필수**에 "예시 값을 바꾸세요".
- `skills`: profile.md 기술 스택 메모의 기술마다 프로젝트 문서에서 근거를 찾아 `evidence`를 만듭니다.
  메모가 비어 있으면 여러 프로젝트에 공통으로 등장하는 기술 위주로 3~8개 고릅니다.
  **근거를 못 찾은 기술은 빼고** 리포트에 알립니다.
- `projects`: profile.md `프로젝트 순서` → 없으면 폴더 이름 순. 순서에 적힌 이름은 실제 `src/` 폴더 이름과 **대소문자까지** 맞춰 보고,
  맞는 폴더가 없는 이름은 싣지 않고 리포트 **필수**에 적습니다.
- §1에서 건너뛴 프로젝트(프로젝트 문서 없음·재료집 단계)는 `projects`에 넣지 않습니다(`profile.md` `프로젝트 순서`에 적혀 있어도 — 그 이름은 리포트에 "문서 없음"으로만 적고 필수로 세지 않음).
- 폴더 이름 하나만 다시 만드는 경우: 그 프로젝트 JSON만 다시 쓰고, `portfolio.json`은 `skills`의 해당 프로젝트 근거와 `projects` 목록, `generatedAt`(오늘 날짜)만 갱신합니다.
  `projects`는 예전 목록을 유지하고 이번 프로젝트가 없으면 위 순서 규칙의 자리에 더합니다. `data/projects/<id>.json`이 없는 폴더(아직 빌드하지 않은 폴더)는 넣지 않고 리포트 `## 프로필`에 "전체 `/portfolio-build`를 실행하면 실립니다"라고 적습니다.

## 4. 검증 (쓰기 전에 반드시)

- [ ] 모든 `section`·`retro.section`의 텍스트가 원문에 제목으로 존재한다 (Grep으로 확인 — **코드 블록 밖의** `#` 줄만 제목)
- [ ] `verbatim: true`인 `intent`는 **부분 문자열 검사**: 글과 원문을 같은 규칙으로 정규화한 뒤
      원문에 글 조각이 부분 문자열로 있어야 통과. 정규화 = 굵게·기울임·백틱 기호(`*` `_` `` ` ``) 제거 → 연속 공백·줄바꿈을 공백 하나로 → 앞뒤 공백 제거
      (파이썬: `re.sub(r'\s+',' ',re.sub(r'[*_`]','',s)).strip()`). 짧은 스크립트로 전부 돌립니다(눈으로 비교하지 않음).
      통과하지 못하면 `verbatim: false`로 바꿉니다(→ "확인해 주세요"). 통과해도 원문 문장의 앞이나 뒤를 떼어 낸 글(접속어 하나라도)이면 `false`입니다
- [ ] `w`·`h`는 파일 머리에서 읽은 값만 있다(읽지 못한 파일은 필드 없음)
- [ ] 모든 URL이 `http(s)://`로 시작한다 (`#`, `(#)`, 빈 링크는 `""` + 리포트)
- [ ] `tags`의 기술명이 원문에 실제로 등장한다. `skills`는 기술명 또는 그 근거가 된 구체 용어가 등장한다
- [ ] `code/`가 있으면: 문서 코드 블록에 나온 **주요 클래스·메서드 이름**이 `code/`에 존재하는지 표본 확인(정의가 아니어도 `code/`의 글에 나오면 존재)
      (불일치는 리포트 **권장** — "문서 코드와 실제 코드가 다릅니다")
- [ ] `portfolio.json`의 `projects`마다 같은 이름(대소문자까지)의 `src/<id>/` 폴더와 `data/projects/<id>.json`이 있다.
      디스크만 보지 말고 `git -c core.quotepath=false ls-files src data/projects`에 나오는 이름도 대소문자까지 같은지 봅니다(GitHub Pages는 git에 올라간 이름으로 보여 줍니다).
      Windows는 대소문자를 무시해 미리보기에서는 열리지만, Pages에서는 JSON 이름이 다르면 그 프로젝트가 포트폴리오 페이지에서 빠지고(슬라이드는 데이터 없음 안내),
      폴더 이름이 다르면 이미지·상세 문서가 404가 됩니다. 대소문자만 다른 예전 JSON은 지운 뒤 새로 씁니다.
      git에 예전 이름이 남아 있으면(Windows의 git은 대소문자만 바꾼 이름 변경을 알아채지 못함) 직접 고치지 말고 리포트 **필수**에
      `git rm -r --cached <예전 경로>` → `git add <새 경로>` → commit · push 순서를 적습니다
- [ ] JSON이 문법적으로 유효하다 (작성 후 다시 읽어 확인. 예: `python -c "import json,sys;json.load(open(sys.argv[1],encoding='utf-8'))" <파일>`
      — Windows에서 한글 출력이 깨지면 `PYTHONIOENCODING=utf-8`)

## 5. 쓰기

- `data/portfolio.json`, `data/projects/<id>.json`(`schemaVersion: 2`)을 씁니다. `generatedAt`은 오늘 날짜.
- 더 이상 `src/`에 없는 프로젝트의 `data/projects/*.json`은 지웁니다 (지우기 전에 목록을 사용자에게 알림).

## 6. 점검 리포트 → `report.md`

`format/01`·`02`·`03`의 체크리스트와 §7의 미리보기 점검으로 판정해 아래 형식으로 씁니다. 같은 기준을 프로젝트마다 똑같이 적용합니다
(예: 자리표시자 링크 `#`는 항상 **권장**, 팀 프로젝트 역할 없음은 항상 **필수**, 장면 안 빨간 띠는 항상 **필수**). **문제와 방향만** 쓰고, 고친 문장을 대신 써 주지 않습니다.

프로젝트 문서는 `format/02`의 **지금 기준 전부**로 봅니다(판정 방법은 `/portfolio-check` §3과 같음):

- 문서 구성(뼈대 + 붙은 모듈)을 먼저 정합니다. [팀]은 개발 인원이 2명 이상이면 필수, [기획]·[일정]은 붙였을 때만 봅니다.
- 5단계와 **AI 협업** 절의 체크 항목. 개요에는 **목표한 경험**, 결론은 **회고**(없으면 필수, 다른 프로젝트 문서에 그대로 붙여도 말이 되는 일반론뿐이면 권장).
- **문서 구조 판정 기준**(개요가 비개발 직군에게 읽히는가 · 소제목이 바로 읽히는가 · 같은 내용을 반복하지 않는가) — 모두 권장. 소제목은 어느 제목이 어떤 규칙에 걸리는지만 알립니다.
- 구현 단위와 기획 단위를 가리지 않습니다. 기획 단위는 코드·클래스 항목 대신 규칙·수치의 관계와 플레이 화면으로 봅니다.
- 리포트에 "What"·"Why"라는 말을 쓰지 않고 "무엇을 만들었는지"·"왜 만들었는지"로 적습니다.

세 등급: **필수**(없으면 포트폴리오 목적을 못 이룸, 배포된 페이지에 빨간 띠가 보임) · **권장**(있으면 확실히 좋아짐) ·
**참고**(취향·다듬기, 그리고 미리보기의 참고 지표 — 빨간 배지는 아니지만 알아 두면 좋은 것).

```markdown
# 포트폴리오 점검 리포트 (YYYY-MM-DD)

## 요약
| 프로젝트 | 문서 구성 | 필수 | 권장 | 참고 | 스크린샷 | 링크 |
|---|---|---|---|---|---|---|
| Switch Strike | 뼈대 + [기획] | 0 | 2 | 1 | 17 / 4~6 | GitHub ✓ · 영상 ✓ |
```

## 7. 미리보기와 마무리 보고

1. 로컬 서버를 백그라운드로 띄웁니다: `python -m http.server 4600` (실패하면 `py -m http.server 4600`).
   이미 떠 있으면 재사용. 브라우저 도구가 있으면 세 페이지를 열어 콘솔 오류·깨진 이미지가 없는지 확인합니다.
   브라우저 도구가 없으면 `CLAUDE.md` 「미리보기」의 headless Chrome 방법(`?pf-audit=1`)으로 같은 `report()` JSON을 읽고 `ready`가 `yes`인지 확인합니다.
   상세 문서도 같습니다(`doc.html?p=<id>&pf-audit=1` — 그림까지 받은 뒤 씀. 상세 문서의 `ready`는 `true`).

   **7-2. 프로젝트마다 프로젝트 상세 문서(`doc.html?p=<id>`)**
   - 프로젝트 문서 안의 이미지가 모두 보이는지 확인합니다.
   - 콘솔 경고 `[doc] Mermaid 렌더 오류`가 보이면 원문 다이어그램 문법 문제입니다(7-1의 예외와 같은 원인 — 리포트 **필수**, 방향만).

   **7-3. 포트폴리오 페이지(`http://localhost:4600/`)**
   — 장면이 아니라 아래로 읽는 한 페이지라 잘림 띠·장면 점검 지표가 없습니다. `await PFPage.whenReady()` 뒤 `PFPage.report()`를 읽습니다
   (브라우저 도구가 없으면 `index.html?pf-audit=1`의 `#pf-audit`, 형식은 7-1과 같음).
   - `sections`에 `portfolio.json`의 프로젝트마다 `p-<폴더>`·`p-<폴더>-core`(기능이 있을 때)가 있어야 합니다. 빠졌으면 그 프로젝트 JSON을 읽지 못한 것 → §4의 이름(대소문자) 검증으로 돌아감.
   - `images.broken`(열리지 않은 그림) → **필수**. 대표 이미지(`cover`)·기능 화면(`highlights[].image`) 경로와 실제 파일 이름(대소문자)을 맞춥니다. 그 프로젝트의 `## 장면 점검`에
     「포트폴리오 페이지」 항목으로 적고 요약 표 개수에 더합니다.
   - `overflowX`가 0보다 크거나 `errors`가 있으면 src/로 고칠 수 없는 렌더러 문제이므로 리포트에 넣지 말고 마무리 보고에서 따로 알립니다.
   - `strings.issues`(문구 표 `theme/strings.tsv` 점검)가 있으면 리포트에 넣지 말고 마무리 보고에서 줄 번호(`line`)와 `detail`을 짧게 알립니다. 표는 수강생이 직접 고치는 파일입니다(CLAUDE.md 원칙 5).
   - 인쇄(A4, 제출 PDF)는 프로젝트마다 소개 1쪽 + 기능 소개 1쪽으로 나뉩니다. 리포트 항목은 아니며, 수강생이 [PDF로 저장]으로 직접 확인합니다.
