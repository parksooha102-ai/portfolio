# 포트폴리오 시각자료 제안

포트폴리오 프로젝트 문서를 읽고, 독자의 이해를 돕고 주장을 뒷받침할 자료(다이어그램, 스크린샷, 사진, GIF·루프 영상, 그래프, 표)를 **어디에, 무엇을** 넣으면 좋을지 점수표로 제안한다.

- 제안만 한다. 자료를 직접 만들거나 문서를 고치지 않는다. 제안 후 사용자가 제작을 요청하면 그건 별도 작업으로 진행한다.
- 배포 환경은 GitHub Pages 정적 웹사이트로 가정하고, 형식 권장도 그 기준으로 한다.
- 직군은 고정하지 않는다. 문서에서 프로젝트 유형을 추론해 맞는 자료를 고른다.

## 핵심 관점: 이해 + 설득

포트폴리오의 자료는 독자의 이해를 돕는 것만으로는 부족하다. "이 사람이 실제로 했고, 잘했다"를 보여줘야 한다. 그래서 이해 기여도 외에 증거력과 기여 가시성을 함께 본다.

자료마다 증명하는 것이 다르다. 문단을 보고 "여기서 무엇을 증명해야 하나"를 먼저 정한 뒤 자료를 고른다.

| 자료 | 증명하는 것 |
|---|---|
| 사진 | 실제로 존재한다 (실물, 현장) |
| GIF·루프 영상 | 실제로 동작한다 (움직임, 인터랙션) |
| 다이어그램 | 이렇게 설계했다 (구조, 흐름) |
| 그래프·표 | 결과가 이렇다 (수치, 비교) |
| 스크린샷 | 이런 화면·결과물이 있다 (정지 상태) |

## 작업 순서

1. **문서 파악**
   - 프로젝트 유형 추론: 웹 프론트엔드, 백엔드, 모바일, 데이터·ML, 하드웨어·임베디드, 게임, 디자인 등. 여러 개가 섞일 수 있다.
   - 개인/팀 여부와 내 역할. 문서에 역할이 드러나지 않으면 기여 점수가 낮게 나올 수밖에 없으니, 출력 상단에 그 사실을 적고 역할을 밝히는 문장을 추가하라고 권한다.
   - 이미 들어 있는 자료 목록 (`![]()`, `<img>`, `<video>`, 임베드).
   - **핵심 메시지 최대 3개**: 독자가 이 문서를 닫은 뒤 기억해야 할 주장. 보통 "무슨 문제를", "어떻게 풀었고", "결과가 어떠나"에서 나온다. 자료는 이 메시지를 돋보이게 하려고 넣는 것이라, 이후 모든 판단의 기준이 된다. M1, M2, M3로 번호를 붙인다.
2. **문단별로 1단계(필요성)를 판단**해 통과한 곳만 후보로 남긴다.
3. **후보마다 2단계(유형 매칭)**로 자료 종류를 정한다.
4. **3단계(점수)**를 매긴다.
5. **과다 방지**: 대표 자료 지정 → 핵심 메시지에 묶기 → 노출 단계 정하기 → 예산 적용 → 배치 간격 (아래 "과다 방지" 절).
6. **자료만 훑기 테스트**로 마지막 점검을 한다.
7. **출력 형식**대로 결과를 낸다.

## 1단계: 여기에 자료가 필요한가

넣을 신호:
- 구성요소가 3개 이상이고 서로 관계가 있다 → 구조
- 순서나 흐름이 있다 ("A가 B를 호출하고 B가…") → 흐름
- 전후 변화를 말한다 ("개선", "단축", "N% 감소") → 비교
- 선택지를 비교했다 ("A 대신 B를 고른 이유") → 트레이드오프
- 눈으로 봐야 아는 것 (UI, 인터랙션, 애니메이션) → 실물
- 시간에 따라 변해서 정지 화면으로는 "동작한다"가 증명되지 않는다 → 움직이는 자료
- 물리적인 결과물이나 현장이 있다 (하드웨어, 전시, 사용자 테스트) → 사진
- 숫자가 2개 이상 나온다 → 차트나 표

빼야 할 신호:
- **삭제 테스트**: 자료를 지워도 문단이 똑같이 이해된다
- 본문 내용을 그대로 그림으로 옮긴 것뿐이다
- 장식에 가깝다 (기술 스택 로고 나열, 스톡 이미지, 단체 사진, 발표하는 모습만 담긴 사진)
- 움직임이 거의 없는데 GIF로 만들려 한다

빼기로 한 곳 중 사용자가 넣고 싶어 할 법한 것(로고 나열 등)은 출력의 "제외한 후보"에 한 줄 이유와 함께 남긴다. 왜 뺐는지 알아야 사용자가 납득하고 스스로 판단할 수 있다.

## 2단계: 어떤 자료가 맞나

### 정지·움직임·영상 고르기
- 정지 상태로 충분하다 → 스크린샷
- 동작 하나를 10초 안에 보여줄 수 있다 → GIF 또는 루프 영상
- 여러 기능이 이어지거나, 30초를 넘거나, 설명·소리가 필요하다 → 영상 (외부 업로드 + 썸네일 링크)
- 스크린샷 3장 이상을 연달아 붙여야 할 것 같다 → 움직이는 자료 후보

### 매칭 표

| 내용 | 추천 자료 | 주의점 |
|---|---|---|
| 시스템 구조 | 아키텍처 다이어그램 | 박스 10개 이하, 내 담당 영역 강조 |
| 요청·데이터 흐름 | 시퀀스 다이어그램, 플로우차트 | 핵심 경로만, 예외 흐름은 따로 |
| 데이터 모델 | 핵심 테이블만 담은 ERD | 전체 ERD는 오히려 방해 |
| 상태 변화 | 상태 다이어그램 | 상태 5~7개 안팎 |
| 성능·지표 개선 | Before/After 그래프, 모니터링 캡처 | 측정 조건(환경, 부하, 표본)을 캡션에 |
| 기술 선택 | 비교표 (기준 × 후보) | 탈락한 후보와 이유까지 |
| UI 기능 | 스크린샷 | 화면 전체보다 해당 부분 크롭 |
| 인터랙션·애니메이션 | 5~10초 GIF·루프 영상 | 동작 하나당 하나 |
| 체감 속도 개선 | Before/After 루프 영상을 나란히 | 같은 조건, 배속·편집 금지 |
| 실시간 기능 (채팅, 알림, 공동 편집) | 두 화면을 동시에 녹화 | 한쪽 입력이 다른 쪽에 반영되는 순간 |
| CLI·터미널 도구 | 터미널 녹화 | 글자 크게, 타이핑 대기 구간은 컷 |
| 트러블슈팅 | 에러 로그·그래프 캡처, 타임라인 | 문제 → 원인 → 해결이 보이게 |
| 핵심 로직 | 코드 블록 (15줄 안팎) | 이미지가 아니라 텍스트로 (검색·복사·접근성) |
| 하드웨어 결과물 | 실물 사진 (전체 1장 + 핵심부 클로즈업) | 배경 정리, 구성요소 라벨 |
| 실제 구동 | 동작 루프 영상 또는 사진 | 전원·센서 반응 등 동작이 보이게 |
| 사용자 테스트·전시 | 현장 사진 | 얼굴 노출 동의 |
| 초기 설계 과정 | 화이트보드·스케치 사진 | 손글씨 판독성, 최종 다이어그램과 나란히 |
| 모델 학습·성능 (ML) | 학습 곡선, 혼동 행렬, 예측 샘플 | 베이스라인과 비교, 검증셋 기준 명시 |
| 데이터 분석 | 핵심 차트 1~2개 | 차트마다 결론 한 문장 |
| 디자인 개선 | Before/After 화면, 디자인 시스템 일부 | 바뀐 지점 표시 |
| 게임 | 플레이 루프 영상 | 핵심 메커닉 하나 |

표에 없는 내용은 "무엇을 증명해야 하나"로 돌아가 가장 가까운 자료를 고른다.

## 3단계: 점수 매기기

### 점수 기준 (각 1~5)

| 기준 | 1 | 3 | 5 |
|---|---|---|---|
| 이해 | 글로도 거의 충분 | 이해가 눈에 띄게 빨라짐 | 자료 없이는 이해가 어려움 |
| 증거 | 주장과 거의 무관 | 주장을 간접적으로 뒷받침 | 주장을 직접 입증 (실측 그래프, 실제 동작) |
| 기여 | 누가 했는지 안 드러남 | 프로젝트 전체 수준 | 내 담당 부분이 명확히 드러남 |
| 용이 | 새로 구현·촬영이 필요 | 녹화·작도에 1~2시간 | 기존 캡처·데이터로 바로 가능 |

**총점 = 이해 + 증거×2 + 기여 + 용이** (최대 25)

증거에 2배를 주는 이유: 일반 문서와 달리 포트폴리오는 읽는 사람이 주장을 의심하며 읽는다. "응답 속도를 개선했다"는 문장보다 실측 그래프가 훨씬 설득력 있다.

**등급**: 20~25 필수 · 14~19 권장 · 13 이하 선택. 등급은 출발점이고, 최종적으로 본문에 들어갈지는 "과다 방지"에서 정한다.

### 채점 예시
- "Redis 캐시 도입으로 p95 1.2s → 180ms" 옆 Before/After 그래프: 이해 4, 증거 5, 기여 4, 용이 4 → 4+10+4+4 = **22 필수**
- 팀 프로젝트 아키텍처 (본인은 결제 모듈 담당), 결제 모듈을 강조한 다이어그램: 이해 5, 증거 3, 기여 4, 용이 3 → 5+6+4+3 = **18 권장**
- 같은 다이어그램인데 담당 영역 강조가 없으면 기여 2 → **16 권장**. 이렇게 점수가 갈리는 이유를 상세에 적어 두면 사용자가 강조 표시를 넣을 동기가 생긴다.
- 기술 스택 소개 문단의 로고 나열: 1단계 삭제 테스트 탈락 → 제외한 후보

### 주의 태그
점수와 별개로, 만들 때 실수하기 쉬운 위험을 태그로 단다. 해당할 때만 붙인다.
- **[보안]** API 키, 토큰, 고객 데이터, 사내 도메인, 내부 대시보드, 회사 NDA 대상. 움직이는 자료는 녹화 중 뜬 알림·탭 이름·북마크바·다른 창까지 프레임 단위로 확인
- **[개인정보]** 사진 속 타인 얼굴, 명찰, 배경 모니터, 화이트보드 내용
- **[정확성]** 기획 단계 다이어그램이 실제 구현과 다를 가능성
- **[정직성]** 성능 증거용 영상에 배속·컷 편집 금지, 그래프 축 왜곡 금지
- **[권리]** 남이 만든 이미지, 회사 자산, 폰트·아이콘 라이선스

## 과다 방지: 중요한 자료가 묻히지 않게

자료가 늘수록 하나하나의 무게가 줄어든다. 각각은 점수가 높아도, 모아 놓으면 대표 자료와 핵심 증거가 다른 자료 사이에 묻힌다. 그래서 점수를 매긴 뒤 아래 순서로 걸러낸다. 목표는 "좋은 자료를 많이"가 아니라 "핵심 메시지마다 가장 강한 자료 하나"다.

### 대표 자료
문서 맨 위에 **대표 자료 1개**를 반드시 지정한다. 핵심 기능이나 결과가 3초 안에 보이는 것. 보통 루프 영상(GIF)이나 결과 그래프가 가장 강하다. 훑어보는 독자는 이것과 캡션만 보고 계속 읽을지 정한다. 대표 자료는 가장 중요한 핵심 메시지를 증명하는 자료 중에서 고른다.

### 1. 핵심 메시지에 묶기
후보마다 어느 핵심 메시지를 증명하는지 연결한다. 연결되는 메시지가 없으면 "보조"로 표시한다.
- **필수** 등급은 핵심 메시지를 증명하는 자료에만 준다. 보조 자료는 20점 이상이어도 권장으로 내린다.
- **메시지마다 본문 자료는 1개**. 같은 메시지를 증명하는 후보가 여럿이면 점수가 가장 높은 하나만 본문에 남긴다. 같은 주장에 붙은 두 번째 자료는 새로 알려주는 게 거의 없고, 첫 번째 자료의 힘만 나눠 가진다.
- 증명할 자료가 없는 핵심 메시지가 있으면 출력 상단에 경고로 적는다. 가장 중요한 주장에 증거가 비어 있다는 뜻이라, 다른 어떤 자료보다 먼저 채워야 한다.

### 2. 노출 단계 정하기
모든 후보를 셋 중 하나로 보낸다.

| 단계 | 대상 | 표시 방법 |
|---|---|---|
| 본문 | 대표 자료, 필수, 예산 안에 드는 권장 | 바로 보이게. 권장은 대표·필수보다 작게 (너비 60~70%) |
| 접기 | 본문에서 밀려났지만 깊이 읽는 독자에게 가치 있는 것 (전체 ERD, 추가 화면, 상세 로그·그래프) | `<details>`로 접어 둔다 |
| 제외 | 선택 등급, 장식, 접어 둘 가치도 없는 중복 | 넣지 않고 "제외한 후보"에 이유 한 줄 |

접기는 "보여주고 싶은 건 많은데 본문이 산만해지는" 상황의 출구다. 면접관처럼 깊이 보는 독자는 열어 보고, 훑는 독자는 지나친다.

### 3. 예산 적용
- 본문 자료는 **대표 1 + 필수 최대 3 + 권장 최대 2 = 최대 6개**. 섹션이 적은 문서는 **섹션 수 + 1**을 넘지 않는다 (둘 중 작은 값).
- **섹션당 본문 자료 1개**.
- **움직이는 자료는 본문에 최대 3개** (대표 포함). 여러 개가 동시에 재생되면 시선이 흩어진다.
- 기존 자료도 예산에 포함한다. 유지하기로 한 기존 자료와 새 제안을 합쳐 상한을 넘지 않게 한다.
- 넘치면 점수, 그다음 우선순위(결과 증거 > 핵심 의사결정 > 문제 상황 > 일반 구조)로 자르고, 잘린 것은 접기나 제외로 보낸다.
- 사용자가 예산을 따로 정하면 그 값을 따른다. 6개는 훑어보는 독자가 기억할 수 있는 정도를 기준으로 잡은 출발점이다.

### 4. 배치 간격
- 본문 자료끼리 연달아 붙이지 않는다. 사이에 최소 한 문단을 둔다. 붙어 있으면 둘 다 약해진다.
- 대표 자료 주변(첫 화면)에는 다른 자료를 두지 않는다.
- 움직이는 자료는 한 화면에 하나만 보이게 떨어뜨린다.

### 5. 자료만 훑기 테스트
출력하기 전에, 본문 자료와 캡션만 위에서 아래로 이어 읽는다고 생각하고 확인한다.
- 핵심 메시지가 모두, 각각 한 번씩 나오는가
- 문제 → 해결 → 결과 흐름으로 이어지는가
- 권장 자료가 필수 자료보다 더 눈에 띄지 않는가. 움직임, 크기, 위치를 본다. 권장인 GIF가 필수인 정지 그래프보다 시선을 끄는다면 권장을 정지 이미지로 바꾸거나 접기로 내린다.

걸리는 게 있으면 고친 뒤 출력한다.

### 추가 요청이 올 때
제안 뒤에 사용자가 자료를 더 넣고 싶어 하면, 예산 안에서 "하나 넣으면 하나 접기"로 어떤 걸 접을지 함께 제안한다. 그래도 넣겠다고 하면 따르되, 어떤 자료가 묻힐 수 있는지 한 줄로 알린다.

## 매체별 제작 가이드

항목별 상세의 "만드는 법"에 해당 내용을 골라 반영한다.

**공통**
- 한 자료에 한 메시지. 캡션은 결론 문장으로 쓴다 ("캐시 도입 후 p95 1.2s → 180ms"). 캡션을 결론으로 쓸 수 없으면 자료의 메시지가 흐린 것이다.
- 자립성: 본문 없이 자료와 캡션만 봐도 이해되게.
- 다이어그램 색상·표기법은 문서 전체에서 통일.

**사진**
- 피사체가 바로 보이게: 크롭, 배경 정리, 초점, 조명
- 내가 만든 부분에 화살표나 라벨
- 실물은 사진, 구조는 다이어그램. 사진 한 장에 구조 설명까지 담으려 하지 않는다.

**GIF·루프 영상**
- 5~10초, 동작 하나
- 첫 프레임에서 잠깐 멈춰 루프의 시작점을 알 수 있게
- 커서와 클릭 위치가 보이게
- 관련 영역만 크롭, 텍스트가 읽히는 해상도
- 첫 프레임만 봐도 의미가 통하게 (미리보기, 인쇄, 재생 실패 대비)

**다이어그램**
- 문단의 추상화 수준에 맞춘다. 개요 문단엔 박스 몇 개, 상세 문단엔 해당 부분만 확대.

**스크린샷**
- 해당 영역만 크롭, 더미 데이터 사용, 개인 정보 가리기

## GitHub Pages 형식 가이드

항목별 상세의 "형식"에 반영한다.

- **다이어그램**: SVG를 기본으로 제안한다. 확대해도 선명하고 가볍다. Mermaid는 github.com 저장소 화면에서는 렌더링되지만 GitHub Pages(Jekyll) 사이트에서는 별도 스크립트나 테마 설정이 없으면 코드 그대로 보일 수 있으니, SVG로 내보내 넣는 쪽을 권한다.
- **스크린샷**: PNG. **사진**: JPG 또는 WebP. 표시 크기의 약 2배 해상도로 리사이즈해 용량을 줄인다.
- **움직이는 자료**: 짧고 작은 건 GIF도 괜찮다. 용량이 커지면 mp4/webm을 `<video autoplay loop muted playsinline>`로 넣는 쪽이 보통 훨씬 가볍다. Jekyll 마크다운 안에 HTML을 그대로 쓸 수 있다.
- **30초 넘는 데모**: YouTube 등에 올리고 썸네일 이미지 + 링크로. GitHub는 100MB 넘는 파일을 거부하고, Pages 사이트에도 1GB 크기 제한과 월 100GB 대역폭 소프트 제한이 있어서 영상 원본을 저장소에 넣기엔 부담이 크다.
- **alt 텍스트**: 모든 이미지에. 스크린리더 사용자와 이미지 로딩 실패에 대비. 캡션과 같은 내용이어도 된다.
- **지연 로딩**: 첫 화면 아래 이미지엔 `loading="lazy"`.
- **접기**: `<details><summary>전체 ERD 보기</summary> … </details>`. 안의 이미지는 `<img>` 태그로 넣는다. 마크다운 이미지 문법은 사이트 설정에 따라 HTML 블록 안에서 변환되지 않을 수 있다.
- **크기 차등**: 권장 자료는 `<img style="width:65%">`처럼 대표·필수보다 작게 넣어 시각적 위계를 만든다.
- **다크 모드**: 투명 배경 다이어그램은 어두운 테마에서 선이 안 보일 수 있다. 흰 배경을 넣거나 사이트 테마를 확인.
- **모바일**: 가로로 넓은 다이어그램은 작은 화면에서 읽기 어렵다. 세로 배치를 고려하거나 원본 크기 링크를 단다.

## 출력 형식

다음 형식을 따른다. 점수표에는 **본문에 넣을 자료만** 싣는다. 접기와 제외는 아래에 짧게 둔다. 제안 결과 자체가 길어지면 사용자도 중요한 제안을 놓치기 때문이다. 점수표는 총점 높은 순으로 정렬하되 대표 자료는 맨 위에 둔다.

```markdown
## 시각자료 제안: {프로젝트명}

> **프로젝트 유형**: {추론한 유형} · **내 역할**: {파악한 역할 또는 "문서에 드러나지 않음 → 역할 문장 추가 권장"}
> **핵심 메시지**: M1 {…} · M2 {…} · M3 {…}
> **대표 자료**: #1 {자료명}
> **예산**: 본문 {n}/{상한} · 접기 {n} · 제외 {n}
> ⚠ {증거가 비어 있는 메시지가 있을 때만: "M2를 증명할 자료가 없음 → {무엇을 확보하면 되는지}"}

### 점수표 (본문)

| # | 위치 | 추천 자료 | 증명할 것 | 이해 | 증거(×2) | 기여 | 용이 | 총점 | 등급 |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 맨 위 (대표) | {자료} | M1 · {한 구절} | 4 | 5 (10) | 4 | 4 | 22 | 필수 |
| 2 | {섹션명} | ... | 보조 · {한 구절} | | | | | | 권장 |

### 항목별 상세

#### 1. {자료명} · {총점}점 · {등급}
- **위치**: {섹션명}의 "{문단 첫 구절}…" 바로 아래
- **캡션 초안**: {결론 문장}
- **만드는 법**: {도구, 범위, 길이 등 2~3줄}
- **형식·크기**: {SVG / PNG / mp4 루프 등과 이유 한 구절, 본문 폭 또는 너비 60~70%}
- **점수 메모**: {점수를 끌어올릴 방법이 있으면 한 줄, 예: "담당 모듈을 강조하면 기여 2→4"}
- **주의**: {태그와 내용, 해당할 때만}

### 접기 자료
| 자료 | 위치 | 접는 이유 | 펼치기 문구 |
|---|---|---|---|
| {자료} | {섹션명} 끝 | {예: M1과 같은 메시지, 예산 초과} | {예: "전체 ERD 보기"} |

### 제외한 후보
- {위치}: {자료} — {이유 한 줄: 선택 등급 / 장식 / 중복 / 예산 초과}

### 기존 자료 점검
| 자료 | 판단 | 이유 |
|---|---|---|
| {파일명 또는 설명} | 유지 / 접기 / 교체 / 삭제 | {한 줄} |
```

- "접기 자료", "제외한 후보", "기존 자료 점검"은 해당하는 게 있을 때만 넣는다.
- 기존 자료는 새 제안과 같은 기준으로 판단하고, 유지한 것은 예산에 센다.
- 프로젝트 문서가 여러 개면 프로젝트별로 따로 낸다.
- 문서가 짧은 초안이라 섹션이 없으면 문단 단위로 위치를 적는다.
- 사용자가 요청한 언어로 낸다.
