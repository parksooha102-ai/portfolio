# 프로젝트 문서 리팩토링

대상: `src/<폴더>/` 바로 아래의 `.md` 하나(프로젝트 문서). 다른 폴더는 건드리지 않습니다.
기준은 `format/02-tech-document.md`(뼈대 + 모듈, AI 협업, 결론 — 회고, 목표한 경험, 문서 구조 판정 기준)와 `format/01-portfolio.md`·`format/03-diagrams.md`입니다.

이 스킬은 `/portfolio-*` 명령이 아니므로 `/portfolio-update`가 교체하거나 지우지 않습니다.

## 지키는 것 (CLAUDE.md 원칙 2·3)

- **지어내지 않습니다.** 문서에 넣는 사실은 지금 문서, 수강생의 답, 소스 레포에서 확인한 것뿐입니다. 목표한 경험·회고·AI 협업에 들어갈 **사실과 소감은 묻고**, 답의 낱말을 살려 씁니다.
- **수강생이 "고쳐 줘"라고 한 범위만** 고칩니다. 제목 바꾸기·절 옮기기·반복 정리·용어 통일 같은 구조 작업은 요청을 받으면 바로 해도 됩니다.
- **Claude가 새로 쓴 문장은 목록으로 보여 주고** 뜻이 맞는지 확인받습니다.
- 커밋·push·다시 빌드는 수강생이 원할 때만 합니다. 제목·절 번호가 바뀌면 다시 빌드 때 슬라이드 장면과 `#s=` 주소가 새로 만들어진다는 것을 미리 알립니다.
- 큰 변경(전체 다시 쓰기) 전에는 지금 판을 scratchpad에 사본으로 남깁니다. 같은 폴더에 `.md`를 하나 더 두지 않습니다(빌드가 폴더의 `.md` 하나를 문서로 읽음).

## 순서

### 1. 점검하고 보여 주기

`/portfolio-check <폴더>`(portfolio-check 스킬)로 점검합니다. `report.md`에 같은 기준의 점검이 이미 있고 그 뒤로 `format/`도 문서도 바뀌지 않았으면 다시 쓰지 않고, 빠진 지적만 더합니다.
수강생에게는 필수·권장·참고를 **줄 번호와 함께** 쉬운 경어체로 보여 주고, "제가 고칠 수 있는 것"과 "답이 필요한 것"으로 나눕니다.

자주 나오는 지적과 판정:

| 지적 | 판정 기준 |
|---|---|
| `1.1 무엇을 (What)`·`1.2 왜 (Why)`·`사용법 —`·`핵심 동작 ①`, 요약의 `**무엇을:**`·`**왜:**` | 틀 이름 라벨 → 권장. 맨 위 요약의 문단 머리 라벨도 같은 규칙 |
| 그림 종류 이름이 제목(`클래스 다이어그램`) | 읽는 사람이 보는 것으로 → 권장 |
| AI 협업이 HTML 주석(✏️)뿐 | 화면에 안 보이므로 "없음" |
| 목표한 경험 | 툴·프레임워크면 '유저'는 쓰는 사람(개발자·기획자). "왜"를 쓴 글이 담고 있으면 인정 |
| 5장 회고 | 이미 "겪은 일 → 알게 된 것 → 다음에는"이면 다시 묶을 필요 없음 |
| 맨 위 한 줄 요약 ↔ 결론 | 미리보기라 반복으로 세지 않음. 실제 반복은 같은 사례를 두 절에서 각각 설명하는 것 |
| 핵심 루프를 그림과 함께 절 하나로 설명 | [기획] 모듈로 봄 → "루프가 목표한 경험을 어떻게 만드는지" 한 줄이 권장으로 붙음 |

### 2. 질문 없이 고칠 수 있는 것 먼저

라벨식 제목, 요약의 라벨, 같은 사례를 두 번 설명하는 표. **절 번호는 바꾸지 않고** 제목 글자만 바꾸면 본문의 "(1.2 참조)" 같은 가리킴이 그대로 맞습니다.

### 3. 수강생에게 사실 묻기

한 메시지에 모아 묻고, 답에 예시를 붙여 쉽게 답하게 합니다.

- **AI 협업:** ① 쓴 도구 ② 맡긴 것 ③ 직접 정한 것 ④ 결과를 확인한 방법 ⑤ 잘 된 일·안 된 일 하나씩. 안 썼으면 한 줄.
  "안 된 일"을 모르겠다고 하면 소스 레포 기록에서 후보를 찾아 묻습니다(아래 4). 없으면 비워 두고 지어 채우지 않습니다.
- **[기획] 연결:** 루프를 되풀이하게 만든 이유. 답이 곧 "루프 ↔ 목표" 연결 문장입니다.
- **개요를 쉽게:** "게임 개발을 모르는 사람에게 두세 문장으로 설명한다면?" — 개요 재료.
- **목표한 경험:** "이것을 쓴 사람이 끝나고 뭐라고 말하면 성공인가?" 물건(프레임워크)의 목표와 **사람이 할 수 있게 되는 것**을 가릅니다.
  결론의 목표 달성 표에 짝이 되는 줄을 넣고, 만든 사람만 써 봤으면 "다른 기획자가 써 보지는 않음"처럼 확인하지 못한 것을 밝힙니다.
- **영상:** 본편·쇼츠 주소.

초안은 답의 낱말로 만들어 보여 주고, 확인받은 뒤 넣습니다.

### 4. 소스 레포와 대조

수강생이 레포 경로를 주면 읽기만 합니다(쓰지 않음).

- 수강생의 기억과 코드가 다를 수 있습니다. 예: "딕셔너리 순회"라고 기억했지만 `Bullet`은 처음부터 `List<IBulletModule>`을 순회했고, 딕셔너리는 다른 곳(`BulletModulePool`, 07-05 추가 → 07-06 삭제, 호출하는 곳 없음)에 있었음. 다르면 근거(파일·커밋 날짜)를 보여 주고 어느 쪽이 맞는지 묻습니다.
- `git log -S '<이름>'`으로 넣었다 지운 코드를 찾으면 "받아들이지 않은 AI 제안" 같은 회고 재료가 나옵니다. AI가 만들었는지는 코드 모양으로 단정하지 않고 묻습니다.
- 문서의 주장(예외 분기, 피격 기록, 되돌린 해결 주석, 엔진 버전 등)을 코드와 표로 대조해 맞음/다름을 알립니다. 문서와 상관없는 코드 문제(남은 `Debug.Log` 등)는 따로 한 줄로만.

### 5. "일기 같다"는 피드백

기술 문서가 "시스템이 어떻고 왜"보다 "내가 그때 무엇을 했고 어땠나"를 앞세울 때 나옵니다. 범위를 말하지 않았으면 문서 전체로 봅니다.

| 신호 | 고치는 방향 |
|---|---|
| 결론 소제목이 고백("~에 시간을 썼다", "~가 반복되었다", "~를 남기지 않았다") | 본문에 이미 있는 **교훈 문장**을 소제목으로. "~할 것이다" → "~한다" |
| 감상으로 끝나는 문장("눈에 띈다", "자연스러워 보였다", "생각보다 어려웠다", "쫓겨") | 사실 문장으로 바꾸거나 덜어냄 |
| 시간 순서 서술("당시", "이번 프로젝트에서는", "시간이 지나 다시 보니") | 시스템 사실은 현재형, 결론을 앞에 |
| 문서 작성 과정 메모("문서를 쓰며 다시 검토했다", "이 점은 5.5에서 회고한다") | "나중에 따져 본 것이다", "(5.4)" |
| AI 협업이 서술형 | 맡긴 것 / 직접 판단한 것 / 확인한 방법 / 잘 된 것 / 받아들이지 않은 것 표 |

트러블슈팅의 과거형, 결정의 "~택했다"는 실제 사건이라 그대로 둡니다.

### 6. 퇴고 체크리스트

- **첫 문장 시험:** 절마다 첫 문장만 이어 읽어 흐름이 잡히는지.
- **한 내용은 한 곳:** 핵심 사례가 몇 번 나오는지 `grep -c`로 셉니다(예: "맨 앞 삽입" 8곳 → 자세한 설명 1곳, 나머지는 가리키기).
- **용어 통일:** 섞인 말을 셉니다(예: 데미지 15 · 피해 9 → 코드와 맞춰 하나로). 처음 나오는 곳에서 한 번 풀어 씁니다(디너지(역시너지), 훅(모듈이 끼어드는 지점)).
- **사람 이름 통일:** 같은 사람을 플레이어·테스터·기획자로 섞어 부르지 않음. 게임 속 캐릭터를 뜻하는 "플레이어"는 그대로.
- **숫자·사실이 서로 맞는지:** 예: "탄환 풀링 도입(최대 27발)" ↔ "수십·수백 발이 아니어서 모듈 풀은 안 씀" → 대상이 탄환인지 모듈 인스턴스인지 밝힘. "재사용 달성" ↔ "다른 프로젝트로 옮기면 전투 시스템까지 따라감" → 범위를 밝힘.
- **면접에서 내 말로 설명할 수 있는가.** AI에게 맡긴 부분은 큰 흐름이라도 말할 수 있게.
- **제목 = 슬라이드 목차.** 20줄 넘는 코드는 슬라이드에서 두 장면.

### 7. "문장은 괜찮은데 전체가 어색하다"는 피드백

여러 번에 걸쳐 덧붙인 문서에서 나옵니다. 짜임새를 진단합니다.

| 원인 | 확인 방법 |
|---|---|
| 앞뒤로 뛰게 만듦 | 절 번호 가리킴 수(장별), 핵심 이야기가 흩어진 절 수 |
| 그림이 설명과 떨어짐 | 그림만 모은 절(예: 2.6 클래스·2.7 시퀀스)이 설명 절과 몇 줄 떨어졌나 |
| 제목 꼴이 제각각 | 명사 / 끝나지 않은 문장 / "A — B" / 질문형 / "A vs B" / 괄호 꼬리표 |
| 장마다 글 틀이 다름 | 굵은 머리말 문단 수, 인용 상자(`>`)가 여러 용도로 쓰임 |
| 끼워 넣은 문장 | 최근 넣은 한 줄짜리 문장이 앞뒤와 이어지는지 |
| 한 장이 여러 일을 함 | 결과·트러블슈팅·부채·계획·배운 점이 한 장에 |

작은 처방(그림 옮기기 · 제목 꼴 · 끼워 넣은 문장)과 큰 처방(핵심 이야기를 한 곳으로)을 나눠 제안합니다. 수강생이 전체를 다시 쓰자고 하면 8로.

### 8. 구성안 합의 후 전체 다시 쓰기

1. **구성안을 먼저** 보여 줍니다: 장마다 "읽는 사람의 질문"·절·지금 문서에서 오는 곳 표. 수강생이 자기 안을 내면 기준에 비춰 조정할 곳만 짚습니다.
   - AI 협업은 부록이 아니라 **결론 앞, 번호 없이**(뼈대의 한 덩어리).
   - GitHub·시연 영상 링크는 **1장**(개발 환경과 함께).
   - 목표한 경험·목표의 전환은 1장에(결론이 가리키므로).
   - 문제 해결 사례는 그 **기능 절 안**에(기준이 권함).
   - 서로 다른 결정 둘을 한 절로 묶으면 안에서 두 덩어리로.
2. 확인받으면 지금 판을 scratchpad에 사본으로 남기고 다시 씁니다. 규칙:
   - 사실·코드 블록·표·그림·숫자는 그대로. 장마다 할 일 하나. 이야기는 한 곳에서 끝냄.
   - 제목은 장 안에서 같은 꼴(결정 장은 "A vs B" 또는 "~을 선택한 이유").
   - 글 틀 고정: 기능 "동작 / 설계 의도", 결정 "결정 대상 / 비교 표 / [결정]", 문제 "문제 / 원인 / 해결 / 결과", 부채 "현상 / 문제"(개선 방향은 표로 따로).
   - 인용 상자는 덧붙임(문서 범위, 기록 없음 메모)에만.
   - 그림 앞뒤에 "이 그림에서 봐야 할 것" 한 줄.
3. **빠진 것 대조** (스크립트로, 눈으로 하지 않음):

```bash
O="<사본>"; N="src/<폴더>/<문서>.md"
for f in "$O" "$N"; do echo "$(basename "$f"): images $(grep -c '!\[' "$f"), fences $(grep -c '^```' "$f"), mermaid $(grep -c '^```mermaid' "$f")"; done
ex(){ awk '/^```/{f=!f; next} f' "$1" | sort; }; diff <(ex "$O") <(ex "$N")     # 코드·그림 본문 (절 번호 주석만 달라야 함)
for t in <숫자·고유명사 목록>; do grep -q -- "$t" "$N" || echo "MISSING: $t"; done
grep -nE '<예전 절 번호 패턴>' "$N"                                            # 남은 옛 가리킴
```

4. 바뀐 점과 **Claude가 새로 쓴 연결 문장 목록**을 보여 줍니다.

### 9. 영상 링크

- 본편 → 1장 개발 환경 표의 "시연 영상". 쇼츠 → 내용이 맞는 절에 `**영상:** [제목 (쇼츠)](주소)` 한 줄(그림 바로 아래). `?feature=share`는 뺍니다.
- 초안 때 만든 영상은 **파일 이름·화면 배지에 예전 절 번호**가 있을 수 있습니다. 구성이 바뀐 절(예: 1.5 → 1.4, 4.5 → 3.5)을 표로 알려 주고, 화면에 번호가 보이면 영상을 고치거나(portfolio-video 스킬) YouTube 제목만 고치도록 안내합니다.
- 영상 내용은 직접 볼 수 없으므로, 제목과 지금 절 내용이 어긋나 보이는 곳(예: "모듈 시너지"인데 그 절은 코드 조립법)은 자리를 묻습니다.

### 10. 마무리

남은 항목을 정리하고 `/portfolio-build <폴더>`로 다시 빌드할지 묻습니다(이 PC에 python이 없으면 `deck-edits.json`이 있는 프로젝트는 메모리 [[no-python-on-pc]] 참고).
다시 점검하려면 `/portfolio-check <폴더>`.

## 참고 — 1-Bullet-Module에서 합의한 최종 구성

```
요약 (무엇 · 왜 · 결과 · 배운 점)
1. 프로젝트 소개      목적과 핵심 아이디어(목표한 경험·목표의 전환·문서 범위) · 63가지 조합 문제(+레퍼런스 차이 표) · 핵심 성과와 개발 환경(+링크) · 시연과 조작 방법[기획]
