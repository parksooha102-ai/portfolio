# 프로젝트 문서 리팩토링

대상: `src/<폴더>/` 바로 아래의 `.md` 하나(프로젝트 문서). 다른 폴더는 건드리지 않습니다.
기준은 `format/02-tech-document.md`(뼈대 + 모듈, AI 협업, 결론 — 회고, 목표한 경험, 문서 구조 판정 기준)와 `format/01-portfolio.md`·`format/03-diagrams.md`입니다.

이 스킬은 `/portfolio-*` 명령이 아니므로 `/portfolio-update`가 교체하거나 지우지 않습니다.

## 지키는 것

**수강생 문서 (CLAUDE.md 원칙 2·3)**
- **지어내지 않습니다.** 문서에 넣는 사실은 지금 문서, 수강생의 답, 소스 레포에서 확인한 것뿐입니다. 목표한 경험·회고·AI 협업·설계 의도에 들어갈 **사실과 소감은 묻고**, 답의 낱말을 살려 씁니다.
- **수강생이 "고쳐 줘"라고 한 범위만** 고칩니다. 제목 바꾸기·절 옮기기·반복 정리·용어 통일·그림 앞 첫 줄 같은 구조 작업은 요청을 받으면 바로 해도 됩니다.
- **Claude가 새로 쓴 문장은 넣기 전에 초안으로 보여 주고**, 넣은 뒤에는 `report.md` "확인해 주세요"에 목록으로 남깁니다.
- 수강생이 기억하지 못하는 숫자(예: "26줄")는 짐작해 고치지 않습니다. 레포에서 확인한 **이름**(메서드·커밋)으로 바꾸거나 그대로 두고 묻습니다.
- 커밋·push는 수강생이 원할 때만 합니다. 커밋은 `git commit -- <이 프로젝트 파일…>`처럼 경로를 지정합니다.
- 큰 변경(전체 다시 쓰기) 전에는 지금 판의 문서와 `data/projects/<id>.json`을 scratchpad에 사본으로 남깁니다. 같은 폴더에 `.md`를 하나 더 두지 않습니다(빌드가 폴더의 `.md` 하나를 문서로 읽음).

**공유 파일 — 여러 세션이 프로젝트마다 나눠 동시에 작업할 수 있습니다**
- `report.md`는 **git에 없는 로컬 파일**이라 지워지면 되살릴 곳이 없습니다. 크게 고치기 전에 scratchpad에 사본을 남깁니다.
- `report.md`는 **고치기 직전에 다시 읽고, 내 프로젝트 부분만 Edit로** 고칩니다. 파일 전체를 다시 쓰지 않습니다.
- 셸로 파일을 고칠 때 `perl -i`(제자리 편집)와 `> 파일` 리다이렉트를 **한 명령에 섞지 않습니다**. 결과를 새 파일에 쓰고, 크기가 0이 아닌지 확인한 뒤에 바꿔 넣습니다.
  (실제로 이 조합 때문에 `report.md`가 빈 파일이 된 적이 있습니다. 그때는 다른 세션의 scratchpad 사본으로 되살리고, 각 세션에 자기 부분을 다시 넣어 달라고 `SendMessage`로 요청했습니다.)
- `data/projects/<id>.json`을 셸로 고칠 때는 JSON을 읽었다 다시 쓰지 말고(Perl `JSON::PP`는 키 순서를 섞음) **글자 단위로 바꿉니다**.

## 0. 진행상황 보고

수강생이 "지금 어디까지 했지", "진행상황 보고 이어서"라고 하면, 대화와 `git status`·`report.md`를 보고 아래 표로 먼저 보여 준 뒤 다음 단계를 진행합니다.

| 단계 | 상태 | 한 일 |
|---|---|---|
| 1. 점검 · 2. 구조 작업 · 3. 사실 묻기 · 4. 레포 대조 · 5. 그림 · 6. 말투·퇴고 · 7. 짜임새 · 8. 다시 쓰기 · 9. 데이터 맞추기 · 10. 영상 · 11. 마무리 | ✅ / ← 지금 / 대기 / 선택 | 한 줄씩 |

## 1. 점검하고 보여 주기

`/portfolio-check <폴더>`(portfolio-check 스킬)로 점검합니다. `report.md`에 같은 기준의 점검이 이미 있고 그 뒤로 `format/`도 문서도 바뀌지 않았으면 다시 쓰지 않고, 빠진 지적만 더합니다. 요약 표의 개수와 본문 항목 수가 맞는지도 봅니다(안 맞으면 빠진 항목을 찾아 더함).
수강생에게는 필수·권장·참고를 **줄 번호와 함께** 쉬운 경어체로 보여 주고, "제가 고칠 수 있는 것"과 "답이 필요한 것"으로 나눕니다.

| 지적 | 판정 기준 |
|---|---|
| `1.1 무엇을 (What)`·`1.2 왜 (Why)`·`사용법 —`·`핵심 동작 ①`·`(API)`·`**(Why)**`, 요약의 `**무엇을:**`·`**왜:**` | 틀 이름 라벨 → 권장. 요약의 `**결과:**`·`**배운 점:**`는 1번 문서 틀이라 둠 |
| 그림 종류 이름이 제목(`클래스 다이어그램`, `클래스 계층`) | 읽는 사람이 보는 것으로 → 권장 |
| AI 협업이 HTML 주석(✏️)뿐 | 화면에 안 보이므로 "없음" |
| 목표한 경험 | 툴·프레임워크면 '유저'는 쓰는 사람(개발자·기획자). "왜"를 쓴 글이 담고 있으면 인정 |
| 5장 회고 | 이미 "겪은 일 → 알게 된 것 → 다음에는"이면 다시 묶을 필요 없음 |
| 맨 위 요약 ↔ 결론, 절 번호로 가리키는 한 줄 | 미리보기·가리키기라 반복으로 세지 않음. 실제 반복은 같은 사례를 두 절에서 각각 **설명**하는 것 |
| 핵심 루프를 그림과 함께 절 하나로 설명 | [기획] 모듈 → "루프가 목표한 경험을 어떻게 만드는지" + "기능마다 목표에 기여하는 한 줄"이 권장으로 붙음 |
| [팀] (2명 이상) | 결론에서 **팀의 결과**와 **내 파트의 결과**를 나눴는지 |
| 숨은 주석의 예전 유형 이름("C. 팀 프로젝트 유형") | 참고. 화면에는 안 보이지만 고쳐 둠 |

## 2. 질문 없이 고칠 수 있는 것 먼저

라벨식 제목, 요약의 라벨, 같은 사례를 두 번 설명하는 문장, 장 제목의 꼬리표(`(기술 부채)`·`— 범위`). **절 번호는 바꾸지 않고** 제목 글자만 바꾸면 본문의 "(1.2 참조)" 같은 가리킴이 그대로 맞습니다.
제목은 "읽는 사람이 화면에서 보는 것" 또는 그 절이 답하는 질문으로 짓되, 본문에 이미 있는 말을 씁니다(예: 결정 절의 "결정 대상" 질문을 줄여 제목으로).
제목이 바뀌면 슬라이드 데이터가 예전 제목을 가리켜 빨간 띠가 생기므로, 고친 뒤 9단계(데이터 맞추기)나 다시 빌드가 필요하다고 알립니다.

## 3. 수강생에게 사실 묻기

**`AskUserQuestion`으로 한 번에 4개까지** 묻습니다. 선택지는 예시이고(수강생은 "기타"에 직접 씀), 답이 다음 질문을 정하면 여러 번에 나눠 묻습니다. 마지막에 초안을 보여 주고 "모두 넣기 / 고칠 곳 있음"으로 확인받습니다.

| 묻는 것 | 질문과 선택지 |
|---|---|
| 목표한 경험 | ① 유저를 누구로 볼지(플레이어 / 그 시스템을 쓰는 팀원 개발자 / 둘 다) → ② "끝나고 뭐라고 말하면 성공인가?"(예시 문장 3개) → ③ 실제로 확인했는지(확인 못 함 / 확인함 — 본 장면을 기타에) |
| AI 협업 | ① 쓴 도구(복수) ② 맡긴 것(복수: 구현·버그 원인·리팩터링·문서·커밋 메시지) ③ 확인한 방법(복수: 코드 읽기·플레이·멀티 테스트·팀원 리뷰) ④ **직접 정한 것** — 선택지는 **문서 4장의 결정들**로 만듦 ⑤ 잘 된 일(맡긴 일에서 후보) ⑥ 안 된 일·받아들이지 않은 제안(비워 두기 / 없음 / 기타) |
| 고르지 않은 결정 | ④에서 빠진 결정은 "어떻게 나왔나요?"(AI 제안을 받아들임 / 팀원과 함께 / 고르는 걸 빠뜨림)로 다시 묻고, 답을 그 결정 절의 `[결정]` 줄에도 반영("팀원과 함께 대안 B를 선택했다") |
| 팀 결과 ([팀]) | 게임 전체가 어디까지 갔나(완성 후 발표·시연 / 플레이테스트 / 개발 중 마감) → 자리(수업 최종 발표 등) |
| [기획] 연결 | 루프를 되풀이하게 만든 이유(예시 2개 + 기타). 이어서 **기능 절마다** 목표에 어떻게 기여하는지 하나씩(예시 3개, "직접 관계없음" 포함) |
| 개요를 쉽게 | 문서의 사실로 만든 두 문장 초안을 보여 주고 "이대로 / 고쳐서" |
| 영상 | 있음(주소를 기타에) / 아직 없음 |

초안은 답의 낱말로 만들고, 답에 없는 말을 이어 붙인 부분은 **굵게** 표시해 보여 줍니다.

## 4. 소스 레포와 대조

수강생이 레포 경로를 주면 읽기만 합니다(쓰지 않음).

```bash
K="<레포>"
git -C "$K" log --format=%B | grep -ci 'co-authored-by'            # AI 공동 작성 표시 (grep 'AI'는 'main'에도 걸리므로 쓰지 않음)
git -C "$K" log --no-merges --author=<이름> --numstat --format='@ %h %ad %s' --date=format:'%m-%d' \
  | grep -E '^@|\.cs$' | awk '/^@/{h=$0; next} {if ($2+0>=15) print h" | -"$2" +"$1" "$3}'   # 크게 지운 커밋
git -C "$K" show <커밋> -- '<파일>' | grep '^[-+][^-+]'               # 지운 줄 직접 보기
```

- 문서의 주장(엔진 버전, 지운 줄 수, 클래스 줄 수, "TSV만 고친 커밋 N건", 인용한 코드 주석)을 코드와 **표로** 대조해 맞음/다름을 알립니다.
- 수강생의 기억과 코드가 다를 수 있습니다(예: "딕셔너리 순회" ↔ 실제로는 `List` 순회, 딕셔너리는 07-05 추가 → 07-06 삭제된 다른 클래스). 근거(파일·커밋 날짜)를 보여 주고 어느 쪽이 맞는지 묻습니다.
- 따옴표 안 문장이 코드·커밋에 없으면 인용이 아니라 요약이므로, 용어 통일 대상입니다(예: "쿨다운을 건다" → "쿨타임").
- AI 흔적이 없으면 AI 협업은 답만으로 씁니다. AI가 만들었는지는 코드 모양으로 단정하지 않습니다.
- 문서와 상관없는 코드 문제(남은 `Debug.Log` 등)는 따로 한 줄로만.

## 5. 그림 고치기

수강생이 그림을 고치자고 하면 `format/03-diagrams.md` 「소스에서 읽히는 것 → 다이어그램」으로 종류를 고르고, **레포 코드에서 호출 순서·이름을 확인해** 그립니다. 넣기 전에 초안을 보여 줍니다.

- **복잡하다고 하면 하는 일 기준으로 나눕니다**(예: "상점 준비 / 카드 목록 그리기"). 화살표 3개 안팎의 쪽은 그림 대신 **문장 한 줄**로 쓰고 나머지만 그림으로 두는 안을 함께 제안합니다(슬라이드도 한 장면).
- 그림 안 라벨은 짧게, 인자는 줄이고, 팀원이 만든 부분은 그림에서 빼고 본문의 "팀원 기여" 줄에 둡니다.
- 상속 그림에 상속·구현이 아닌 협력 클래스(의존 화살표만)가 섞여 있으면 뺍니다(역할 표·코드에 이미 있으면 내용이 빠지지 않음).
- **Mermaid `classDiagram`은 `Foo`와 `Foo~T~`를 한 상자로 합칩니다.** 제네릭 쪽은 id와 라벨을 따로 줍니다: `class FooT["Foo&lt;T&gt;"] { … }`, 관계도 `FooT`로.
- 넣은 뒤 상세 문서에서 `PFDoc.report().diagrams.failed`가 비었는지, 상자 수가 맞는지 확인합니다.
- 슬라이드 장면의 그림 지문(`fp`, mermaid 첫 줄 예: `flowchart LR` → `sequenceDiagram`)도 함께 바꿉니다(9단계).

## 6. 말투와 퇴고

**"일기 같다"는 신호**

| 신호 | 고치는 방향 |
|---|---|
| 결론 소제목이 고백("~에 시간을 썼다", "~를 남기지 않았다") | 본문에 이미 있는 **교훈 문장**을 소제목으로. "~할 것이다·~하려고 한다" → "~한다" |
| 감상으로 끝나는 문장("눈에 띈다", "생각보다 어려웠다") | 사실 문장으로 바꾸거나 덜어냄 |
| 시간 순서 서술("당시", "이번 프로젝트에서는") | 시스템 사실은 현재형, 결론을 앞에 |
| 문서 작성 과정 메모("이 점은 5.5에서 회고한다") | "(5.4)" |
| AI 협업이 서술형 | 맡긴 것 / 직접 판단한 것 / 확인한 방법 / 잘 된 것 / 받아들이지 않은 것 표 |

트러블슈팅의 과거형, 결정의 "~택했다"는 실제 사건이라 그대로 둡니다.

**퇴고 체크리스트** — 문장을 더한 뒤에는 **커밋 전에 한 번 더** 돕니다(덧붙인 문장끼리 겹치기 쉬움).

- **첫 문장 시험:** 절마다 첫 문장만 이어 읽기. 그림·표로 시작하는 절은 "이 그림에서 봐야 할 것" 한 줄(그림 안의 사실만으로).
- **한 내용은 한 곳:** 핵심 사례가 몇 번 나오는지 `grep -c`. 같은 소개가 두 절에 있으면(예: 게임 소개가 1.1과 1.3에) 한 곳으로.
- **요약 ↔ 본문 숫자:** 요약의 주장이 본문보다 크지 않은지(예: 요약 "16줄과 TSV 한 줄" ↔ 본문 "16줄 + TSV 한 줄 + 프리팹").
- **용어 통일과 첫 풀이:** 섞인 말을 셉니다(쿨타임 51 · 쿨다운 2 → 코드 인용만 남김). 처음 나오는 곳에서 풀어 쓰고, **풀이보다 앞에 쓰인 곳**이 없는지 봅니다(TSV(탭으로 칸을 나눈 표 파일), ScriptableObject(Unity의 데이터 에셋), 릴리스(떼기)).
- **사람 이름 통일:** 같은 사람을 다르게 부르지 않음(서버 담당 팀원 → 역할표대로 "팀원 A").
- **숫자·사실이 서로 맞는지**, **면접에서 내 말로 설명할 수 있는지**.
- **제목 = 슬라이드 목차.** 20줄 넘는 코드는 슬라이드에서 두 장면.

## 7. 짜임새 진단 ("문장은 괜찮은데 전체가 어색하다")

여러 번 덧붙인 문서에서 나옵니다. 숫자로 잽니다:

```bash
f="src/<폴더>/<문서>.md"
awk '/^```/{c=!c} !c && /^## /{ch=$0} !c{while(match($0,/[(（ ]?[1-5]\.[1-5](-[1-3])?[)）]/)){p[ch]++; $0=substr($0,RSTART+RLENGTH)}} END{for(k in p) print p[k]"\t"k}' "$f"   # 장별 절 번호 가리킴
grep -nE '^#{2,4} ' "$f"                                                                                  # 제목 꼴
awk '/^```/{c=!c} !c && /^## /{ch=$0} !c && /^\*\*[^*]+\*\*/{b[ch]++} END{for(k in b) print b[k]"\t"k}' "$f"   # 장별 굵은 머리말
grep -n '^>' "$f"                                                                                         # 인용 상자 쓰임
```

| 원인 | 판정 |
|---|---|
| 핵심 이야기가 흩어짐 | 한 이야기(예: "쿨타임 한 곳 · bool 의미 · 서버 검증")가 몇 절에 나오나. 5곳 이상이면 큰 원인 |
| 한 장이 여러 일 | 결론 장에 결과·트러블슈팅·부채·배운 점이 다 있음 → 슬라이드에서도 결론 장 표지가 남음 |
| 제목 꼴이 섞임 | 같은 장 안에서 명사 / 끝나지 않은 문장 / 질문형 / "A — B" / 괄호 꼬리표 |
| 인용 상자의 쓰임이 여럿 | 요약·메모·장 안내·코드 주석 인용 |
| 그림이 설명과 떨어짐 | 그림만 모은 절이 설명 절과 몇 줄 떨어졌나 |

작은 처방(제목 꼴 · 인용 상자 · 끼워 넣은 문장)과 큰 처방(이야기를 한 곳으로 · 장의 할 일 나누기)을 나눠 제안합니다. 큰 처방을 고르면 8로.

## 8. 구성안 합의 후 다시 쓰기

### 8-1. 다른 프로젝트 문서와의 통일 먼저 보기

포트폴리오의 문서들이 **같은 사람이 쓴 것처럼** 보여야 합니다. 이미 고친 다른 프로젝트 문서(지금은 `src/1-Bullet-Module/기술문서.md`)의 장 이름과 글 틀을 읽고 맞춥니다.
수강생 기준: **"완전히 다른 사람이 쓴 것처럼 보이지만 않으면 형식을 완전히 베낄 필요는 없다."**

| 맞추는 것 (한눈에 보이는 뼈대와 말투) | 그대로 둬도 되는 것 (프로젝트마다 다름) |
|---|---|
| 장 이름(1. 프로젝트 소개 · 2. 시스템 구조 · 3. 핵심 기능과 구현 · 4. 설계 결정과 트러블슈팅 · AI 협업 · 5. 결과와 회고) | 절 제목과 그 꼴(질문형 결정 제목 등) |
| 맨 위 요약: 한 줄 소개 → 무엇·왜 한 문단 → `**결과:**`·`**배운 점:**` | 장 안의 절 순서 |
| 개발 환경을 **표 하나**로(Engine·Language·Core·기간·AI 활용·GitHub·시연 영상) | 표를 몇 개로 나눌지(부채·개선 표 하나 / 둘) |
| `> **문서 범위** —` 상자 | 부록 |
| 문제 해결 사례는 기능 절 안 `####`, 맞는 기능 절이 없으면 4장 | [팀] 절(팀 프로젝트에만) |
| AI 협업 표 머리 `\| \| 내용 \|`, "<도구>에게 맡긴 것" | |
| 5.1 **"목표 (1장) \| 결과" 표** + (팀이면) 팀의 결과 한 줄 | |
| 배운 점은 **교훈 문장을 굵은 소제목**으로, 아래 근거 한두 줄 | |
| 굵은 머리말은 `**설계 의도:**`처럼 콜론으로 | |

구성안을 처음에 1번을 그대로 베껴 내면 "너무 많이 바꾼다"는 반응이 나올 수 있습니다. 위 표의 왼쪽만 맞춘 **줄인 안**을 먼저 내는 편이 낫습니다.

### 8-2. 구성안

장마다 "읽는 사람의 질문"·절·지금 문서에서 오는 곳·(통일이면) 다른 문서와 맞춘 점 표로 보여 줍니다.
- AI 협업은 부록이 아니라 **결론 앞, 번호 없이**.
- 목표한 경험은 1장에(결론의 목표 달성 표가 가리키므로).
- 결론 장에는 회고만(결과·부채·배운 점). 트러블슈팅을 결론 장에 두면 슬라이드에 결론 장 표지가 남습니다.
- 절 번호 가리킴 목록("이 문서에서 다루는 내용")은 문서 범위 상자 안 한 문장으로 줄이고, 그 안의 **용어 첫 풀이**는 잃지 않게 옮깁니다.
- 바뀌는 슬라이드 주소(없어지는 장 표지 `#s=ch-…` 등)를 미리 알립니다. 장면 key는 이어 쓰므로 대부분 그대로 열립니다.

### 8-3. 다시 쓰기

확인받으면 사본을 남기고 **Write로 전체를 한 번에** 씁니다. 규칙:
- 사실·코드 블록·표 내용·그림·숫자는 그대로. 장마다 할 일 하나. 이야기는 한 곳에서 끝냄.
- 글 틀 고정: 기능 "동작 / 설계 의도", 결정 "결정 대상 / 비교 표 / [결정]", 문제 "문제 / 원인 / 해결 / 결과".
- 인용 상자는 덧붙임(문서 범위, 팀원 기여, 기록 없음 메모)과 코드 주석 인용에만.
- 옛 절 번호 가리킴은 모두 새 번호로(사례를 `####`로 옮겼으면 "3.2 「사례 제목」").

### 8-4. 빠진 것 대조 (스크립트로, 눈으로 하지 않음)

```bash
O="<사본>"; N="src/<폴더>/<문서>.md"
for f in "$O" "$N"; do echo "$(basename "$f"): images $(grep -c '!\[' "$f"), fences $(grep -c '^```' "$f"), mermaid $(grep -c '^```mermaid' "$f"), tables $(grep -c '^|---' "$f")"; done
ex(){ awk '/^```/{f=!f; next} f' "$1" | sort; }; diff <(ex "$O") <(ex "$N") && echo "코드·그림 본문 같음"
for t in <숫자·고유명사·핵심 구절 목록>; do grep -q -- "$t" "$N" || echo "MISSING: $t"; done
grep -nE '<예전 절 번호 패턴>' "$N"        # 남은 옛 가리킴
```

빠진 구절(예: 배운 점의 "찾기 어려운 버그")이 나오면 새 자리에 되살립니다. 바뀐 점과 **Claude가 새로 쓴 문장 목록**을 보여 줍니다.
